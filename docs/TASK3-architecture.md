Task 3: Code Quality and Architecture

The short version of how I would structure Branda V2 is: App Router for routing and rendering, feature folders for code, server components by default, and a small number of client components where there is real interaction.

Component architecture and reusable components. I split components into three groups. Primitives live in components/ui (button, card, input, select), these are themeable and rarely change. Shared composites live in components (layout Header and Footer, shared Price and SkeletonCard, small helpers like EmptyState and BottomDrawer). Feature specific pieces live next to their feature in features/service/components, features/cart/components and so on. One component per file, one export per component, no page containing markup that should be a component. Pages compose, they do not build. The Price component is a good example of why this matters, every place that shows money goes through it so a currency change is one edit.

Folder and file structure. Feature based folders: features/service, features/service-detail, features/cart, features/market. Each has its own components, api, types and utils, so when the cart grows nobody has to touch the service code. Shared types in types/brand.ts. Mock data in data/. Route files stay in app/ only.

For routing, app/[market] holds every customer facing route so /ng, /us, /uk and /ca all share the same templates through a market layout. Route groups would separate the three surfaces: app/(marketing) for public pages, app/(app) for the customer ordering flow, and app/(dashboard) for role based dashboards with their own layout, nav and auth guard. Loading, error and not-found files sit at each segment so failures degrade locally instead of blanking the whole app.

State management. Server state and client state are different things and I keep them apart. Data from the API is fetched in server components and passed down, or through React Query when the client needs to refetch. Filters and sorting are not stored in state at all, they live in the URL search params so a shared link reproduces the exact result set and search engines can index it. The cart is the one piece of real client state, Zustand with localStorage persistence. Small things like an open drawer or an input value are plain useState. I avoid putting server data in context or global stores because it goes stale and it is hard to debug.

API and service layer. Components never call fetch directly. Each feature exposes typed functions in its api folder (getServices, getServiceBySlug, getRelatedServices) and components import those. Right now they read mock JSON, later the same functions hit a real endpoint and nothing in the UI changes. A shared axios client in lib/ handles the base URL, headers and error normalization. Responses get typed, and for anything user supplied I parse with Zod so bad data fails loudly instead of rendering undefined.

Form handling and validation. React Hook Form with Zod resolvers for checkout and any form with more than one field, because it keeps validation in one schema that both the form and the API can use. Small single field inputs like search stay controlled with local state. For mutations, server actions where the flow is server driven, otherwise the API layer with a toast on failure.

Error handling. Three levels. Route segment error.tsx boundaries catch rendering failures and show a retry UI. not-found.tsx handles bad slugs and unknown markets with a 404. Async action failures (add to cart, checkout submit) get caught and surfaced through toasts so the user is never left staring at a silent no-op. Empty states are their own component instead of a blank div.

Authentication and user state. Auth.js (NextAuth) with social providers and email, sessions in httpOnly cookies so tokens never touch localStorage. Middleware protects routes by path, and the session carries a role (customer, staff, admin). Each role gets its own route group with a layout that checks the role and redirects, so access control is enforced on the server rather than hidden buttons. Protected dashboards render behind that guard. Guest checkout stays possible, the cart already persists locally.

Multi market, multi currency and localization. One MarketConfig per market (code, country, flag, currency, symbol, exchange rate, hero copy, featured services) is the single source of truth. The [market] segment validates against it and 404s on anything else. Every price renders through the Price component which formats using the market currency. Metadata is generated per route with generateMetadata using the market and slug. For SEO across markets I generate canonical plus hreflang alternates (en-NG, en-US, en-GB, en-CA, en and x-default) through one helper in features/market/utils/seo.ts, which is now wired into the home, listing and detail pages. If real translation is added later it would be a messages folder per locale with the same URL structure, and the hreflang set already exists to point at it.

Responsive design. Mobile first breakpoints, one container class that handles the max width and gutters, and components change behaviour across breakpoints not just spacing. The service filters are the example I would point at: full filter bar that sticks under the header on desktop, and on mobile it collapses to a single icon button that opens a bottom drawer. Touch targets are at least 40px, text never relies on hover, and the mobile nav is a full screen menu instead of a squeezed desktop bar.

Code maintainability, testing and documentation. TypeScript strict, ESLint, one component per file, no duplicated logic, design tokens as CSS variables in globals so color or radius changes happen in one place. Vitest with React Testing Library for components and pure utils (cart totals, filtering, currency formatting), Playwright for the critical paths (search, filter, add to cart, checkout confirmation). README with setup and decisions, docs/ for the written parts of this task. Storybook is worth adding once the primitive set grows.

Git and version control. Trunk based development, short lived feature branches off main, conventional commits (feat, fix, chore), one PR per feature with a review, preview deployment per PR so QA happens on a real URL, and never committing secrets or lockfile noise. Rebase before merge to keep history linear, and keep main always deployable.
