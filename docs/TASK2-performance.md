Task 2: Frontend Performance and Problem Solving

Before changing anything I would measure first. Run Lighthouse with mobile emulation, check the network tab to see what actually gets downloaded, use React DevTools Profiler for re-renders, run next build with bundle analyzer, and look at server logs for slow API calls. Most of the time the real problem shows up in one of those and the rest of the list is noise.

The likely causes for a slow Next.js app in production are usually a mix of these: unoptimized oversized images that block the LCP, too much JavaScript shipped to the browser for what is basically a content page, client components doing work that should have stayed on the server, too many small API requests per page, and third party scripts blocking the main thread. Here is how I would work through each area.

Image optimization. The largest contentful paint is almost always the hero or the first product image. I would use next/image everywhere, serve AVIF or WebP, set a proper sizes attribute so a phone never downloads a 1920px asset, lazy load anything below the fold, and add priority or fetchPriority only to the LCP image so the browser knows what matters. Explicit width and height (or aspect ratio) on every image to keep CLS at zero, and a blur placeholder on the listing cards so there is no empty gap while loading.

Lazy loading and dynamic imports. Server components are the default so most code never becomes client JavaScript at all. For things that only make sense in the browser, like a chart, a modal, a map or a heavy widget, I would use next/dynamic with a loading fallback. Third party or rarely used UI gets dynamic imported too. The rule I follow is not to dynamic import everything, because splitting too much causes layout jumps and waterfall loading, only genuinely heavy or rarely needed modules.

Code splitting. Next.js already splits per route, so the main thing is to protect that. Avoid importing whole libraries where a small function would do, avoid barrel files that pull an entire feature into a page bundle, import icons from the specific path rather than the whole set, and when there is a big vendor dependency used across many routes I would configure a manual vendor chunk so app code changes do not invalidate it.

Caching. Several layers. fetch cache with next.revalidate for API reads that change rarely, segment level revalidate for catalog pages, CDN caching with proper cache-control headers and stale-while-revalidate so a revalidation never blocks a user, and browser caching with immutable hashed assets. ISR is the right fit for a service catalog where prices and content change maybe once a day. For static mock data like this build, it just gets generated at build time.

API request optimization. Deduplicate identical in flight requests with React cache on the server or React Query on the client, batch related calls into one, and never fire a request per keystroke, search inputs get debounced (400ms in this app). On server components I fetch in parallel with Promise.all instead of awaiting one after another, which removes waterfall latency, and I move data fetching up to the layout or page so it happens once instead of in every leaf component.

Component optimization. Keep components as server components unless they need state or event handlers, that alone removes the biggest re-render cost. On the client side, memoize children only when props are actually stable and expensive, useMemo and useCallback where the alternative is recreating a function or object every render, avoid context providers that change value on every render because everything under them re-renders, use stable keys in lists, and virtualize long lists if they go past a couple hundred rows.

Bundle optimization. I would add @next/bundle-analyzer, look for duplicate dependencies, full imports of libraries that support tree shaking (dayjs and lodash are common offenders), and check for polyfills shipped to modern browsers. Tree shaking works when the code is side effect free ES modules, so package.json sideEffects and import style matter. Third party scripts (chat widgets, analytics, heatmaps) get loaded after interaction or with next/script strategy lazyOnload, unused tags get removed, and self hosted fonts via next/font avoid the extra requests.

Rendering strategy. SSG for marketing, catalog and service detail pages because they are the same for everyone, which is what this build does with generateStaticParams. SSR for anything that depends on the request, session, live inventory or personalised pricing. ISR when content changes on the scale of minutes or hours and you want a fast cached page with background refresh. Streaming with Suspense for dashboards where different widgets finish at different times, so a slow panel does not block the whole page. Client side rendering only for genuinely realtime or private UI where caching would be wrong.

Mobile performance. JS budget for the first load, images sized for small screens, no hover only interactions, avoid long tasks on the main thread since mid range phones are what Lighthouse grades against. Test with CPU throttling and a slow network profile, keep fonts limited to the weights actually used, and watch out for anything that causes scroll jank like large blur or backdrop filters.

Core Web Vitals. For LCP: fast server response, preload the LCP image, priority on it, avoid lazy loading the thing that defines the first screen. For INP: reduce main thread work, break up long tasks, defer non urgent JavaScript, keep event handlers cheap, and stop unnecessary re-renders on input. For CLS: explicit dimensions on images, video and embeds, reserve space for banners and badges that get injected later, never insert content above existing content after load.

Finally I would set budgets in CI, run Lighthouse on pull requests, and track the real user numbers in CrUX or Vercel Analytics so improvements are proven with field data and not just lab scores.
